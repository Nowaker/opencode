## Goals

- A prompt or notice stored while a run is between its last history read and its release is answered.
- A noReply note stored in the same window still starts no turn.

## Root cause

- `runLoop` in `packages/opencode/src/session/prompt.ts` breaks with `exiting loop` once the newest assistant step finished on stop and answers the newest user message it read. The run then still waits for its background snapshots (`processor.settle`, added by [async snapshots](../features/2026-11-01-async-snapshots.md)) before `Runner` goes idle: 4 to 12 s on desktop at load ~50.
- A prompt stored in that window found the runner `Running`, so `ensureRunning` in `packages/opencode/src/effect/runner.ts` joined the run (`case "Running": return [awaitDone(st.run.done), st]`) and got its result, the old answer. Nothing read history again, so the prompt stayed unanswered until the next unrelated prompt.
- Live repro: demo session `ses_e385330dbffecE52YqOIuWaTHZ`, OMO notice `msg_1c7cc86f5001` stored at 23:30:32.120Z, the same millisecond as the loop's last read (`loop step=2`, then `exiting loop` 5 ms later). In the demo runs below, step 1 likewise stays open until just after the notice lands, so in production the race is that read against the notice's commit.
- Every sender goes through `admit` -> `loop`, so typed prompts, vtps, plugin prompts and OMO notices all hit it; a noReply note never calls the loop.

## Fix

- `Runner.ensureRunning(work, again?)`: a caller joining a running run registers a check. `finishRun` asks the run's checks under the state lock when the run succeeds; if any holds, it starts the same work again with the same `done` deferred, so every caller gets the second result and `onIdle` fires once. A failed or cancelled run never reruns. A caller arriving after the decision finds the runner idle and starts its own run.
- `SessionPrompt` passes `unread(sessionID, messageID)`: true unless the joined run's `seen` (reads) or `withdrawn` (unqueue) set has the message, reusing the per-run sets from the queued-prompt work. `loop()` passes the newest stored user message, which covers callers that store input before calling it (the summarize route's compaction request).
- Both `queued_prompts` modes take this path: in `turn_end` a held prompt is never marked seen, so the run reruns and answers it as its own turn.
